## Definitions

- **Oracle**: expected part numbers are computed in `dataset.py` by plain equality filters over the stored records, independently of the search engine. The oracle reads the same extracted records, so it measures interpretation and matching, not extraction accuracy (see the extraction regression tests for that).
- **Exact-match precision**: of all results the system labelled `EXACT_MATCH` across the whole set, the share that the oracle also lists. Any exact result on a query that expects none counts against it.
- **Recall@5**: for queries with expected parts, |top 5 ∩ expected| / min(5, |expected|); for alternative-needed queries the expected part is the record the query was derived from.
- **Hard-constraint violation**: a returned result whose thread or product type differs from the one stated in the query (checked from the query's generation metadata).
- **Latency**: wall-clock per query in-process (no HTTP). Retrieval + ranking excludes query interpretation; end-to-end includes it, and in `auto` mode includes the local LLM call when one was made.

## Limitations

- The queries are template-generated from catalogue records; they are not real user queries, and the informal wording covers only the synonyms listed in the generator.
- This query set was also used while developing the system: four cases that failed in an earlier run (a dimension bound to a keyword across a comma, a bare number treated as a request, and a weak alternative) led to fixes. The figures therefore describe a set the system was tuned on, not unseen data.
- No human has reviewed the results. `data/reports/human_review_sample.csv` (28 rows) is prepared for that review and its reviewer columns are empty.
- Extracted values were spot-checked against the PDFs by the automated regression tests (`backend/tests/test_extraction.py`, 12 records), not exhaustively.
- LLM-mode results depend on the local model and can vary between model versions; rules-only results are deterministic.
- Latency figures are from this machine only.
